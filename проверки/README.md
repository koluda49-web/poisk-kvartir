# Проверки перед отправкой сайта

Две небольшие проверки. Обе требуют, чтобы сервер уже был запущен.

## Как запускать

В одном окне поднимаем сайт:

```
npm start
```

В другом окне запускаем проверки:

```
npm test                    проверит поиск, фильтры и кэш
npm run проверка-страниц    проверит главную, выдачу и страницы под поиск
npm run проверка-страницы   проверит, что скрипт страницы не сломан
```

Обе можно натравить и на живой сайт — просто допиши адрес:

```
npm test https://poisk-kvartir.onrender.com
npm run проверка-страниц https://poisk-kvartir.onrender.com
npm run проверка-страницы https://poisk-kvartir.onrender.com
```

Если всё хорошо — в конце будет «провалено 0». Если что-то сломалось,
проверка напишет, что именно, и завершится с ошибкой.

## Что они ловят

**`поиск-и-кэш.mjs`** — две разные беды сразу:

- фильтр снова начал ходить к Kufar, Realt и Flatbook вместо того, чтобы
  брать данные из памяти (видно по времени ответа). Из-за этого сайт
  тормозит, а источники получают лишнюю нагрузку;
- фильтр стал возвращать не то. Результат сверяется с тем, что получится,
  если отфильтровать базовый список вручную.

Порог «быстро» проверка вычисляет сама: до локального сервера ответ идёт
5 мс, а до Render только сеть съедает 250 мс, поэтому фиксированное число
не подошло бы.

**`страницы-и-выдача.mjs`** — что видит человек и что видит поисковик:

- главная снова отдаётся пустой, и первые секунды вместо квартир видна форма;
- в выдаче стало заметно меньше вариантов — не потерялись ли объявления;
- сломались страницы под поиск (`/minsk`, `/minsk-nedorogo`, `/brest-usadby`).

Отдельно там сторожевая проверка про склейку дублей. Однажды мы склеили
объявления по «телефон + цена» — и оказалось, что так схлопываются РАЗНЫЕ
квартиры одного хозяина: в Минске 59 таких групп. Дублей же между Kufar,
Realt и Flatbook нет вообще, проверено почти на 900 объявлениях. Проверка
следит, чтобы склейка не вернулась.

**`скрипт-страницы.mjs`** — что страница вообще заработает у посетителя.
Страница собирается на сервере как одна большая строка, и внутри неё легко
испортить экранирование: скажем, `\n` превратится в настоящий перенос строки
и разорвёт код пополам. Сайт при этом отдаётся с кодом 200 и внешне выглядит
живым, но не работает ни поиск, ни карта, ни фильтры. Команда `node -c`
такое не находит — она смотрит только на сам сервер, а не на то, что он
отдаёт браузеру. Эта проверка один раз уже поймала именно такую поломку.

## Перед каждой отправкой на GitHub

```
node -c kvartiry-server.js     синтаксис сервера
npm run проверка-страницы      скрипт страницы цел
npm test                       поиск и фильтры работают
npm run проверка-страниц       главная и страницы под поиск на месте
```

## Переключение вкладок — `npm run проверка-вкладок`

Открывает сайт в настоящем Chrome и переключает вкладки в разные моменты
загрузки. Ловит ошибку, из-за которой при переходе на «Что посетить» в ленте
оставались квартиры: ответ поиска жилья приходил уже после того, как
нарисовались места, и затирал их своими карточками.

На быстром ответе ошибка не видна. Чтобы увидеть её своими глазами, запустите
копию сервера с задержкой в `/api/search` — старый код падает на всех
переключениях, нынешний проходит.

## Почему пустой ответ источника живёт в памяти меньше минуты

Проверками это не покрыто: чтобы увидеть, нужен источник, который один раз
не ответил. Опыт ставится копией сервера, где `flatbookRaw` при первом
обращении возвращает пустой список.

На старом коде такой сервер отдавал «Flatbook 0» и через минуту, и через
две — пустой список честно лежал в кэше весь срок, и все посетители
считали, что источника нет. Сейчас пустой ответ держится 45 секунд:
следующий посетитель спрашивает источник заново.
